# gpu-swap

**GPU 显存到 CPU 内存的热度感知迁移层**

> 🎓 先读 [GUIDE.md](GUIDE.md) — 完整的 6 步学习指南

当 GPU 显存不够时，把冷 KV Cache block 换出到 CPU pinned 内存，需要时换回。
换出策略由 [kvcache-tracer](../kvcache-tracer/) 的 trace 数据驱动，不是拍脑袋的 LRU。

这是一个**真的跑过数据**的实现：`libgpuswap.so` 是 nvcc 编的 CUDA 库，Python 通过
ctypes 驱动它跑工作负载，报告里的每个数字都能用下面的命令重跑出来。

## 快速开始

```bash
cd gpu-swap

# 端到端：真库跑一遍合成 workload

# 全策略 × 全预算档对比（+ 热块阈值扫描），出 results/COMPARISON_REPORT.md
python3 scripts/compare_strategies.py --backend real --sweep

# 合成 workload 的保真度对账（生命周期分位 vs 项目一实测）
python3 scripts/check_workload.py
# 策略本身的 CPU 开销（GUIDE Step 5 Q4）
make bench

# 阈值是从项目一 trace 现算的，改了 trace 就重算：
make check-thresholds     # 校验 include/policy_thresholds.h 和数据源指纹是否一致
make thresholds           # 重算并覆盖
```

## 要解决的问题

LLM 推理的显存瓶颈不在权重，在 KV Cache：

- 模型权重占约 14 GB（Qwen2.5-7B FP16）—— 固定成本，推理前就吃掉了
- KV Cache **每个并发请求**占 0.5–5 GB —— 随并发度和上下文长度线性增长
- 本机的 RTX 4090 有 47.4 GB（`./build/test_async` 会打出来；常见配置是 24 GB）

并发一上来，KV Cache 就把显存吃光了，而 KV Cache 是**可以换出去**的：它不参与
梯度，只被读，而且一个 block 被换出去最多是"下次要多算一次 attention"，不是
"算错"。所以问题变成：**显存不够时，换哪个 block 出去？**

vLLM 的默认答案是简单 LRU。本项目要回答的是"如果知道 block 的真实访问模式，
能不能做得更好"，以及"好多少、在什么条件下好"。

## 架构

```
GPU 热池 (受限)              CPU 冷池 (充裕, pinned)
┌──────────────┐            ┌──────────────────┐
│ hot block    │            │ cold block       │
│ hot block    │  ←──→      │ cold block       │      swap_stream_（**单条**）
│ hot block    │  PCIe 异步 │ cold block       │      ─ D2H / H2D 全排这一条
│   ...        │            │   ...            │
└──────────────┘            └──────────────────┘
       ↑                             ↑
       └──── IEvictionPolicy ────────┘
             LRU / LFU / GDSF / Adaptive
             （Adaptive 的常数来自项目一 trace）
```

### 三笔独立的账，不是一个 `in_gpu` 布尔

`GUIDE.md` 的参考骨架用一个 `in_gpu` 同时表达了三件事，于是异步一上来就自相矛盾。
现在拆成三个正交的量：

| 量 | 含义 | 什么时候变 |
|---|---|---|
| **预算占用** `hot_used_bytes` | 这块字节算在谁的预算里 | **发起时**登记。在途换出的字节继续算热池（显存还没还），在途换回的字节发起时就算热池 |
| **槽位归属** `slot` | 这块显存地址归谁 | 发起时就过户（靠单流顺序性，见下） |
| **数据有效性** `in_gpu` | 能不能读 | **只在收割时**翻转 |

准入判断用时间线末端的口径：`hot_used + size <= hot_capacity`。冷池有完全对称的
口径 —— 在途换出已经 pin 住了真实内存，所以 `cold_held` 也是发起时登记。

这条设计推出两个硬约束，都在测试里钉住了：

- **访问器不推进状态机。** `hot_used_bytes()` / `pending_migrations()` 这类读操作
  不会顺带收割在途迁移。所以 `evict(); pending_migrations() == 1` 是**确定性**的，
  跟拷贝快不快、机器忙不忙无关 —— 异步契约因此可测。
- **`free()` 拒绝在途的块，也拒绝被 pin 的块。** 换出可以靠 stream 顺序做安全
  （D2H 排在 reader 后面），释放不行 —— 释放之后那块显存分给别人而读者还在读，
  就是 use-after-free。

## 五个非显然的实现决定

### 1. 迁移路径上不许出现 `cudaMalloc` / `cudaFree`（用 arena）

`cuda_runtime_api.h:4826-4831` 明写：只有 `cudaMallocAsync` 出来的指针不做隐式同步，
**"For all other pointers, this API may perform implicit synchronization."**
也就是"事件完成后 `cudaFree`"这条路会让**整个设备静默串行化** —— 而异步测试照样
通过（数据是对的），只是 host 被拖住、性能全废。这是最难发现的一类 bug：
正确性全绿，性能全丢。

所以构造时按 `hot_pool_bytes` 一次 `cudaMalloc` 出整块 arena，之后所有热池子分配
都在 arena 内部切分（2 MB 对齐，对齐 DMA 才有效率）。收益：预算与实际占用严格相等、
**收割时零 CUDA 调用**（提交变成纯记账）、失败回滚也是纯记账。

### 2. `cudaMallocHost` 是隐式同步点 —— 必须预热冷池

冷池是惰性按 chunk（32 槽）`cudaMallocHost` 的。而 `cudaMallocHost` 本身是"页锁定
主机内存分配"，**属于跨 stream 同步点**。于是第一次换出才去分配冷池时，那次换出会
**等前面所有 kernel 跑完** —— 异步性恰好在最需要它的那一刻失效。

这不是推理出来的，是实测撞上的：一个 250 ms 的自旋 kernel 能把紧随其后的一次
2 MB 换出整个挡住，于是 **pin 的负对照也"通过"了** —— 测试因此假绿。
修法是 `reserve_cold(n)`，在任何 kernel 之前先把槽位分配好（见 `gpu_swap.h:161-176`）。

### 3. 单条 swap stream 是够的，理由是带宽不是带宽上限

vLLM 的做法是每次迁移开一条 stream。本项目用单条，理由是可算的：

- 项目一实测 D2H 渐近带宽 17.5 GB/s、单块迁移 52.4 µs（917 KB 的块）
- 单条 stream 约 1.1 GB/s 的干扰红线（≈1200 块/s）远低于单流的服务能力
- 而且**双向带宽不可加**（PCIe 聚合 ~20 GB/s，D2H 满了 H2D 就没了）

所以多开 stream 换不到吞吐，只换来调度开销和"哪条流上有什么"的复杂度。

### 4. pin 是**顺序约束**，不是否决权

骨架的 pin 是宿主互斥 —— **假锁**：推理 kernel 在 infer stream 上排队 → 调用者
unpin → 管理器立刻在 swap_stream 上发 D2H，**两者之间没有任何 CUDA 依赖**，
拷贝引擎读的正是那个 kernel 正在写的显存。而 E2E 测试根本不碰 infer stream，
所以这个竞态在 E2E 里 100% 不可见。

正确做法是 `cudaStreamWaitEvent(swap_stream_, reader_done)`（`GUIDE.md:349-351`
描述的 vLLM 真实迁移层就是这么做的）。语义因此是：

- 自动挑 victim 时**绕开** pinned 块（有更好的候选）
- 显式 `evict_to_cold` **照做**，只是 D2H 排在 reader 后面
- `free()` **拒绝** pinned 块（`ERR_PINNED`）—— 见上面三笔账那节

验法不靠计时：让一个 kernel 花几百毫秒把整块写成 marker，再换出、换回、读回来。
上了 pin 读到 marker，**不上 pin 读到旧花样**（负对照）。这个判据不受机器快慢影响。

### 5. 策略必须是确定性的，逐出序列要有指纹

模拟时钟下大量 block 同刻，`select_victim` 只比 `last_access` 的话，谁赢由
`unordered_map` 的桶序决定 —— 同一 workload 跑两遍能得到不同的逐出序列。
项目一为此吃过亏（12 次运行 12 个不同的逐出指纹）。所以：

- 每个策略并列时按 `(last_access, block_id)` **字典序**打破
- 逐出序列折进一个顺序敏感的 CRC32（`gsm_eviction_fingerprint`）

聚合计数分辨不出"两个策略是否做了同样的决策"，顺序敏感指纹可以。这是最便宜、
最有说服力的"确实验证到了决策"的证据。

## 实测数据

所有数字都可以用上面的命令重跑。硬件：RTX 4090（sm_89, 128 SM, 47.4 GB）+ EPYC 7B13。

### 异步：重叠是真的（而且有负对照）

`./build/test_async`：

```
── 换出立即返回（访问器不 poll，所以这是确定性判据）
  发起 65.0 MB 用了 0.101ms（约合 641 GB/s 的提交速率）；等它落地总共 3.13ms（30.9×）

── 重叠率（含负对照）
  重叠(并行)  infer=212.00ms swap=4.66ms union=212.00ms → overlap=1.000
  负对照(串行) infer=192.94ms swap=4.93ms union=197.87ms → overlap=-0.000
  达到带宽: 21.58 GB/s
  块速率: 10292 块/s

── pin 是 CUDA 侧的顺序约束（真锁 vs 假锁）
  上了 pin ：落进冷池再读回来 = marker ✓ (首字 0xDEADBEEF)
  不上 pin ：落进冷池再读回来 = 旧花样 ✓(负对照如期) (首字 0x0BADF00D)
```

⚠️ 上面是**一次代表性运行**。带宽那一栏逐次波动在 **20.5–24.4 GB/s**（±8%），
**重叠率则每次都是 1.000 / −0.000** —— 前者是吞吐读数、会随机器状态飘，
后者是结构性读数、不该飘。**判据只立在后者上**，前者只用来对照项目一那条红线。

两点值得单独说：

- **判据不是 `max(t_infer, t_swap) < t_infer + t_swap`。** 那个式子对任意正数
  a、b 都成立（等价于 `min(a,b) > 0`），是恒真的空断言，永远不会失败。用的是
  跨度口径 `overlap = (t_infer + t_swap - t_union) / min(...)`，1 = 完全重叠、
  0 = 完全串行。**并且必须有负对照**（把两段工作串到一条流上重测），否则分不清
  "测到了重叠"和"这个方法根本测不出串行"。
- **"立即返回"不靠计时验。** 因为访问器不 poll，`evict()` 之后
  `pending_migrations() == 1`、`in_gpu` 未翻转、预算未扣减，这三条是确定性的。

### 重叠 ≠ 免费

重叠说的是两段工作**在时间上**不互相等待，**没说谁也没被拖慢**。这件事要分成
两个方向量，而两个方向的答案**不一样**：

**方向一：算力占着 GPU 时，拷贝还能跑多快？**（`test_interference`，同一批 96 MB，
唯一差别是有没有 kernel 在跑；三档 × 3 次取中位数，每次都校验"拷贝结束时 kernel
确实还在跑"）

```
  空载（无 kernel）                :  21.38 GB/s  (10195 块/s)   [3/3 次有效]
  算力受限（6 个只碰寄存器的 kernel）  :  20.75 GB/s  ( 9893 块/s)   [3/3 次有效，3 次确认重叠]
  访存受限（6 个扫 256MB 的 kernel）  :  22.52 GB/s  (10737 块/s)   [3/3 次有效，3 次确认重叠]
```

三个数在噪声里（多次运行落在 0.86x–1.08x，均值≈1.0），**看不出系统性影响**。
这在物理上讲得通：D2H 走 copy engine，瓶颈是 PCIe 链路，而算力根本不用那条链路。

**方向二：拷贝跑着时，算力被拖慢多少？**（`test_copy_slows_compute` —— 这才是
项目一红线的口径，量的是 kernel 的**耗时**，不是拷贝的带宽）

```
  推理 kernel 单独跑            :   3.98 ms
  与 96 MB 的 D2H 同时跑        :   4.03 ms   （拷贝本身 4.26 ms，23.6 GB/s）
```

三次独立运行：**+0.48% / +1.13% / +2.46%**，全部为正。项目一红线的敏感度是
**0.13%**（`pcie_interference_redline.txt`：baseline 步中位数 15.404 ms，噪声底
0.020 ms）—— 所以这个拖慢虽然只有百分之一量级，**已经是他们噪声底的 4–19 倍**，
方向上也和他们一致。**机制最可能是 DRAM**：拷贝引擎读显存（~21 GB/s），
而访存受限的 kernel 也在读显存，两者抢的是同一块 DRAM 带宽。

所以结论要**分开说**，不能合成一句话：

- **重叠是真的**（方向一 + 重叠率 1.000）—— 换出不会把推理**挡住**。
- **免费是假的**（方向二）—— 换出会让同时在跑的推理 kernel 慢约 1%。
- **项目一那条 1.1 GB/s 的红线，本项目没有推翻也没有复现**：他们的测量是在
  真实 vLLM decode 上做的（延迟敏感、步长只有 15.4 ms），本次是在一个 4 ms 的
  批量流式 kernel 上做的。**本测试跑在 21–24 GB/s，是他们红线的 19 倍** ——
  即便在这个远高于红线的速率下也只看到 ~1%，说明效应强烈依赖于 kernel 的
  敏感度，不能拿这里的"只有 1%"去否定他们那条线。

⚠️ 两个测量上的坑，都是实测撞出来的：

1. **判据不能是"倍数是多少"，得是"这次有没有量到东西"。** 第一版没校验
   "拷贝结束时 kernel 还在不在跑"，于是连跑 5 次得到 2 次 1.2x、3 次 1.0x 的
   双峰结果 —— 而两种读数**看起来都合理**。现在每轮显式 `cudaStreamQuery`
   确认重叠，并在输出里报"3/3 次确认重叠"。
2. **两种条件必须交错测，不能先跑完 A 再跑完 B。** 分开跑时两批之间的 GPU
   状态漂移会整个算进差值，实测出现过 **−0.15% 的"拖慢"** —— 物理上不可能为负，
   那个负号就是漂移的读数。交错之后符号就稳定了。

### 策略对比（真库 `libgpuswap.so`）

60 个请求 / 种子 42 / 2 MB 块 / 峰值足迹 1016 MB（508 槽）。预算按**峰值足迹的百分比**
给 —— 不是拍脑袋的 `[8,4,2,1] GB`（那四档每一档都比全部数据还大，见下面 Q2）：

| 预算 | 逐出 | 换回 | LRU | LFU | GDSF | Adaptive |
|---|---|---|---|---|---|---|
| 12.5%（63 槽） | 92.3k | 91.4k | **98.07%** | **89.32%** | 96.21% | 92.82% |
| 25.0%（127 槽） | 77.6k | 77.2k | **96.78%** | **69.37%** | 81.23% | 73.66% |
| 50.0%（254 槽） | 54.5k | 54.3k | **91.62%** | **42.02%** | 57.10% | 44.17% |
| 100.0%（508 槽） | 1 | 0 | — | — | — | — |

（最后一行标为**本档无效**：预算 = 峰值足迹时一次逐出都没真的发生，四个策略全是
0.00% miss。照抄项目一 `policy_report.py` 的规矩 —— "本档无效"必须显式报出来，
不能静静地混在有效数据里。）

**同一份 workload、同一个策略，模拟器和真库的对照**（计划里的验证项 4）：

| 档位 | 策略 | 真库 | 模拟器 | 差 |
|---|---|---|---|---|
| 25% | LRU | 96.78% | 96.76% | 0.02 pp |
| 25% | GDSF | 81.23% | 81.18% | **0.05 pp** |
| 25% | Adaptive | 73.66% | 72.32% | 1.34 pp |
| 50% | GDSF | 57.10% | 57.06% | **0.04 pp** |
| 50% | Adaptive | 44.17% | 48.95% | 4.78 pp |

LRU/LFU/GDSF 对到小数点后一位以内 —— 两条完全独立的实现（C++ 真库 vs Python
模拟器）走同一份 workload 得到同一个逐出序列，说明模拟器没有建模错误。
Adaptive 还差 1–5 pp，因为它多一层"分位数 → 夹断 → 松手"的有状态逻辑，
两层实现在那个状态机上有细微差别 —— 这是**已知且已量化**的残差，不是未知偏差。

#### 踩过的坑：模拟器报了**另一个策略**的保护率

上面那 1–5 pp 的残差是修复之后的结果。修复之前，同一个 E2E 跑出来是：

| | 真库 | 模拟器 |
|---|---|---|
| miss 率 | 33.61% | 34.2% |
| `protect_mean` | **0.368** | **0.8385** |
| `protect_first_quartile` | 0.3976 | 0.7576 |
| `protect_last_quartile` | 0.1869 | 0.9569 |

**同一个策略，保护率差了 47 个百分点，而且时间趋势一个是下行、一个是上行。**
两边的数字都自己说得通，所以只看任何一边都发现不了。

根因是模拟器里一行赋错：

```python
fresh = [b for b in gpu_blocks if b.access_count <= cutoff]
young_hits = len(fresh)          # ✗ 装的是"非热块总数"，名字却叫 young
candidates = [b for b in fresh if self.now - b.alloc_time >= self.young_age_ms]
```

真库那边 `young_hits` 数的是**年轻的那批**，模拟器数的是**全部非热块** ——
于是模拟器上报的是 `1 − 热块占比`（0.8385 ≈ 1 − 0.1615），真库上报的是
`(young + hot)/n`（0.368 ≈ 0.2048 + 0.1637）。分母一样，分子根本不是一回事。

同一个函数里还藏着第二个：分位算的是

```python
s = sorted(self.protect_rates)   # ✗ 排完序再切四分位
```

那是**取值分布**的四分位，不是**时间序**的。所以两边一个报"保护率在下行"、
一个报"在上行" —— 而"保护率随时间怎么变"正是判断策略有没有退化的关键读数，
报反了比不报更糟。

修完之后：

| | 真库 | 模拟器 |
|---|---|---|
| `protect_mean` | 0.3684 | 0.3634 |
| `protect_min` | 0.0202 | 0.0202 |
| `protect_max` | 0.8185 | 0.8185 |
| `protect_first_quartile` | 0.3976 | 0.4062 |
| `protect_last_quartile` | 0.1869 | 0.1695 |
| `inflation` | 35.2098 | 35.21 |

**这条是"双实现"的典型代价**：两份代码做同一件事，漂移的地方恰好是**没人会去
对的那个统计量** —— 因为 miss 率对上了，你会以为"实现对上了"。本仓库的规矩是
真库和模拟器必须能互相解释，所以每加一个上报字段，都要在两边同时看一遍。

#### 修复通胀退化前后的真库实测

同一套命令、同一个 workload，只换内核：

| 档位 | GDSF 修前 | GDSF 修后 | Adaptive 修前 | Adaptive 修后 |
|---|---|---|---|---|
| 12.5% | 96.30% | 96.21% | 96.20% | **92.82%** |
| 25.0% | 85.39% | **81.23%** | 83.88% | **73.66%** |
| 50.0% | 69.80% | **57.10%** | 62.43% | **44.17%** |

修得越多的地方正是逐出越多的地方（50% 档 GDSF −12.7 pp、Adaptive −18.3 pp），
而 12.5% 档几乎没动 —— 那档通胀还没涨到能盖过频率项。**这个形状本身就是
"通胀退化"的诊断**，比任何解释都直接。

#### 踩过的坑：这一节差点整轮跑的是旧内核

上面的数字是**重建之后**重跑的。第一次跑完 16 格时，它量的其实是**修复前**的
`eviction_policy.h` —— 头文件 23:08 改的，`libgpuswap.so` 是 22:59 编的，早了 9 分钟。

危险的地方不是"跑了旧代码"，而是**旧代码的结果看起来完全正常**：趋势对、量级对、
和 LFU/基线的相对关系也对。只把 `--mock`（模拟器，Python 直接读头文件的常数）
拉出来对账才露馅 —— 同一个策略，真库 83.88% 而模拟器 72.32%，差了 11 个百分点。

根因是 `Makefile` 的规则只写了 `src/%.cu`，**没有任何头文件依赖** —— 改了
`include/*.h`，`make` 会说"无事可做"。两层修：

1. `$(HEADERS)` 作为显式前置依赖（钝器，但本仓只有几个头，全量重编约 30 s）
   + `-MMD -MP` 生成精确依赖。⚠️ 光有 `-MMD` 不够：`.d` 文件是**构建之后**才有的
   依赖，对一个已存在的 `build/` 目录**起不了引导作用**，第一次加上它时 `make`
   依然回答"无事可做"。这条是实际撞上的。
2. `scripts/gsm.py` 在 `dlopen` 之前比对源码与 `.so` 的 mtime，旧了就**拒绝加载**
   并打印是哪个文件旧（`GSM_ALLOW_STALE=1` 可绕过）。守卫本身也验了：
   拿一个 2020 年的假 `.so` 去调，确认它真的会炸，而不是个摆设。

这条和上面"恒真的断言""verify 永远不失败"是同一类错误 —— **测试没坏，是它测的
东西已经不是你以为的那个了**。

### 热块阈值扫描

25% 预算那档，扫 `hot_access_threshold`（T）× 三种规则组合，全部真库：

| T | ①只有绝对阈值<br>保护率 / miss | ②+年龄规则<br>保护率 / miss | ③+夹断（现版）<br>保护率 / miss |
|---|---|---|---|
| 0 | 100.0% / 82.10% | 100.0% / 82.10% | 52.4% / **80.64%** |
| 1 | 100.0% / 85.26% | 100.0% / 85.26% | 52.4% / **80.64%** |
| 50 | 88.5% / 80.66% | 94.6% / 77.73% | 54.7% / **73.66%** |
| 121 | 4.0% / 80.20% | 40.2% / **73.80%** | 34.9% / 79.58% |
| 456 | 0.0% / 81.23% | 33.4% / 79.78% | 33.4% / 79.78% |
| 1<<30（关掉） | 0.0% / 81.23% | 33.4% / 79.78% | 33.4% / 79.78% |

读这张表要注意**保护率那一列才是主结论，miss 那一列是配角**：

**1. 绝对阈值不是旋钮，是悬崖。** T 从 50 走到 121（2.4 倍），保护率从 88.5% 掉到
4.0% —— 同一个 workload、同一个策略，隔一档就换了个行为。而跨 workload 更糟：
同一个 T=50 在项目一的 long-summarize 上保护 **98.9%**、在 legacy-c1 上保护 **27.0%**
（极差 72.6 个百分点）。**任何常数都是"在某个 workload 上调对了"。**

**2. 夹断把悬崖修成了平台。** 加上夹断后，六个 T 的保护率全落在 33.4%–54.7%
（33.4% 是年龄规则自己贡献的，夹断只约束热块规则、上限 30%）。再看 miss 那列：
有夹断的极差是 7.0 pp（73.66–80.64），没夹断的极差是 11.5 pp（73.80–85.26）。

也就是说 —— **夹断买到的不是"更低的 miss"，而是"T 猜错也没关系"**。诚实地说，这张表里
最好的单点是 T=121 + 年龄规则（73.80%），**没有**用夹断；用夹断的那条最好的单点是
T=50 的 73.66%。两者基本打平。夹断的价值在别处：不夹断时，猜错 T 的代价是
11.5 pp（T=1 的 85.26%），夹断之后最差也就 80.64%。**它是方差压缩器，不是优化器** ——
这个区别在做"参数该定多少"的决策时是决定性的。

**3. 一条不太舒服但必须说的观察：这个绝对阈值旋钮本身几乎不影响结果。**
看 ① 那一列，保护率从 0% 拉到 100%，miss 只在 80.20%–85.26% 之间动。原因是
`select_victim` 在候选集被清空时会逐级松手，而松手的落点就是打分内核 ——
保护率 100% 那两行（82.10%）几乎正好等于纯 GDSF（81.23%）。**规则不是在选人，
是在决定自己什么时候失效。** 这解释了为什么"占位符 T=50"没有立刻炸出人命的
数字：它坏得很安静。

**4. `松手` 计数是这条退化链的仪表盘。** T=0/T=1 那几行有 ~155k 次松手（几乎每次
决策都在松），T=456 那几行是 1275 次。这个计数**不是**内部实现细节，它是
"你的保护规则正在空转"的直接读数 —— 项目一那个 `tau=63ms → adaptive ≡ LRU`
的坑，当时没有任何仪表能看见。

### 策略自身的 CPU 开销（GUIDE Step 5 Q4）

`make bench`，不碰 CUDA，直接喂驻留集给 `select_victim`：

```
驻留块数        LRU      LFU      GDSF   Adaptive        （us/次决策）
64            0.088    0.052    0.256      0.552
512           0.858    0.486    2.050      4.741
2048          3.523    1.925    8.366     18.094
8192         14.103    8.206   40.598     81.200

相对一次换出（52.4 us）的比例：
    512 块: LRU=1.64%  LFU=0.93%  GDSF=3.91%  Adaptive=9.05%
   2048 块: LRU=6.72%  LFU=3.67%  GDSF=15.97% Adaptive=34.53%
   8192 块: LRU=26.91% LFU=15.66% GDSF=77.48% Adaptive=154.96%
```

每块的开销是**常数**（LRU 1.7 ns、LFU 0.9 ns、GDSF 4–5 ns、Adaptive 8.5–10 ns），
所以是 O(n) 不是 O(n log n)：全排序被 `nth_element` 换掉了，GDSF 的 `base_` 表是
每决策一次哈希查找而不是排序。

⚠️ 实测撞到的坑：第一版基准量出来 LRU/LFU 是 **0.000 us** —— 编译器把整个循环删了
（两个策略都是纯函数、返回值没被消费、没有副作用）。GDSF/Adaptive 有可变成员所以
留了下来，于是表格里"最简单的策略最快"这个结论完全是假的。现在基准必须消费返回值。

## Step 5 五问的答案

**Q1：什么样的 workload 下 Adaptive 显著优于 LRU？**

热池装不下工作集、且**访问模式是"每轮扫过全部活跃块"**的时候，LRU 会剧烈抖动。
本次 workload（合成，60 请求 / 508 块峰值）就是这种：LRU 因为"每轮把刚换出的块
又换回来"而近乎全 miss。

差距的**形状有点反直觉，要照实说**：

| 预算 | LRU | Adaptive | 差 |
|---|---|---|---|
| 12.5%（63 槽） | 98.07% | 92.82% | 5.3 pp |
| 25.0%（127 槽） | 96.78% | 73.66% | 23.1 pp |
| 50.0%（254 槽） | 91.62% | 44.17% | **47.5 pp** |

**差距随预算变宽而放大，不是变紧**（再往上到 100% 就整档失效了）。原因是
预算极紧时**谁都救不了**：63 个槽装不下任何有意义的工作集，再聪明的策略也只能
在"几乎全 miss"里挑，天花板本身就在那儿。真正能拉开差距的区间是"装得下一部分、
但装不下全部" —— 也正是 LRU 的"每轮把刚换出的块换回来"最致命的区间。

**Q2：什么情况下 Adaptive 和 LRU 差不多？**

两种情况，本仓库都实测到过：

1. **热池装得下工作集**。预算 = 峰值足迹那档一次逐出都没有，四个策略全是 0% miss。
   这正是骨架版对比表失效的原因：它的四档预算是 `[8,4,2,1] GB`，而 workload 的
   峰值足迹只有 192 MiB —— **每一档都比全部数据还大**，表格很整齐，什么都没测。
   现在预算按**峰值足迹的比例**给，并且逐出次数可忽略的档位会在报告里标"本档无效"。
2. **策略静默退化，规则失去作用。** 骨架版的 `hot_access_threshold = 50` 在这份
   workload 上保护了 84% 的块（高于这个 workload 的读次数 P50=192 以下的绝大多数），
   候选集常年为空 —— 当时的实现掉进一个"随便选一个"的 `fallback` 分支，于是
   adaptive 的四档 miss 率和小数点后两位**都等于 LRU**。项目一为同一个坑栽过一次
   （`tau = 63ms → adaptive ≡ LRU`），这是第三次。

   ⚠️ **机制订正**：重写之后 fallback 没了（改成"逐级松手 + 计数"，见上），所以
   **"退化成 LRU"这个说法只对旧实现成立**。新实现退化到的是**打分内核** ——
   上面扫描表里保护率 100% 那两行的 miss（82.10%）几乎正好等于纯 GDSF（81.23%），
   而不是 LRU 的 96.78%。同样是静默退化，但落点不同，**这也是为什么新实现必须
   报"松手/夹断"计数**：不报的话，这两种退化在输出里长得一模一样。

**Q3：策略选择对"换回延迟"的影响有多大？**

⚠️ 先把单位对齐，否则这一问很容易算错：**项目一的 52.4 µs 是 917 KB 的块**，
而 gpu-swap 用的是 **2 MB** 的块。按本项目实测的 ~21 GB/s，一个 2 MB 块
**≈ 100 µs**（项目一那个数字里约 23% 是 28 个描述符的固定开销，与块大小无关）。

在 50% 预算那档，LRU 与 Adaptive 的 miss 率差 47.5 个百分点 —— 也就是
**每 1000 次块访问多出 475 次换回，约 47 ms 的 PCIe 时间**。

对 P99 的影响要更尖锐，因为**换回是同步的**：读者要等换回落地才能继续，
一次 2 MB 换回 ≈ 100 µs 直接叠在 decode 步长上（实测中位数 15.4 ms，是它的 0.65%）。
**单次不致命，数量才致命** —— 这正好解释了为什么 miss 率的差别在吞吐上看不明显，
却能在尾延迟上炸出来。

**但必须配这条红线**：换出速率超过约 1.1 GB/s 就会把 decode 步长拖出噪声底。
也就是说 miss 率不是越低越好 —— **换得越勤，干扰越大**。上面两个干扰测试
分别从拷贝侧和推理侧量了这件事，见「重叠 ≠ 免费」。

**Q4：Adaptive 的额外开销有多大？超过好处了吗？**

见上面的 `make bench`。结论是**分水岭很清楚**：

- 驻留集 ≤ 512 块（≈1 GB 热池，本项目 E2E 的实际规模）：开销 ≤ 4.7 µs/决策，
  是换出代价（52.4 µs）的 **9%**。相比它省下的 47 个百分点 miss，完全划算。
- 驻留集 8192 块（≈16 GB 热池）：开销 81 µs/决策，是换出代价的 **155%** ——
  策略比它优化的那件事本身还贵，**这时候不该用**。

所以 GUIDE 提的"不要 O(n²)"还不够：**O(n) 也会在大驻留集上变成主要开销**。
真正的分水岭是"每次决策的开销 vs 一次换出的开销"，不是复杂度的阶。

**Q5：如果 CXL 可用（延迟降 25–50 倍），策略还重要吗？**

本项目的数据支持一个反直觉的答案：**硬件越快，策略越重要，但重要的地方变了。**

- 迁出/换回变得便宜 → 单次 miss 的代价下降 → miss 率本身没那么要命
- 但换回来的**带宽是共享的**，而带宽不会因为 CXL 而变多（PCIe 的红线就是证据：
  超过 1.1 GB/s 干扰就看得见）。CXL 只降低延迟，不增加带宽
- 所以策略的作用从"少换几次"转成"**别在同一时刻集中换**" —— 也就是把迁移
  在时间上摊平，而不是在数量上压减。这恰好是单一 swap stream + 异步提交
  （而不是同步换出）带来的东西

换句话说：**硬件越快，越应该让策略去管"什么时候换"，而不是"换不换"。**

## 合成 workload 的保真度

`scripts/check_workload.py` 把合成 workload 的块生命周期分位和项目一实测的放在一起：

```
轮长 60.0 ms   请求 30   种子 42
access 事件 1575   块次访问 48597   峰值足迹 994 MB (497 块)

类型         n |   合成 P10     P25     P50     P90 |   实测 P10     P25     P50     P90
----------------------------------------------------------------------------------------
short     17 |      600    1080    1260    1800 |      472    1056    1403    1908   (short-qa)
medium     9 |     2280    3720    5100    6840 |     1921    4204    5263    7315   (code-gen)
long       4 |     4740    7020    7080    7740 |     4429    5192    6138    7808   (long-summarize)
----------------------------------------------------------------------------------------
年龄规则（young < 710 ms）覆盖的生命周期比例: 中位数 41%  P90 100%
```

P25 那一列基本对上了（1080 vs 1056 —— 710 ms 这个阈值就是从它导出的），P50 略低、
P90 略高，三个 workload 类型的**相对次序**也对。**中位数覆盖 41%** 意味着年龄规则
在这份 workload 上有区分度：它保护的是不到一半的块，不是全体。

这一步不是形式主义。`include/policy_thresholds.h` 里的年龄阈值（710 ms）是从
真实 trace 的**生命周期 P25** 导出的 —— 如果合成 workload 的时间轴不是同一刻度，
这个阈值就是另一个意思上的数字，而且从结果里看不出来。

骨架版本正是这样：每轮推进 0.5 s、而且**轮数 = 请求数**（一轮 = 一次到达 +
所有活跃请求各前进一步），于是 30 个请求就只有 30 轮，块的整个生命周期都被压在
710 ms 的"年轻"窗口里 —— 年龄规则不是在保护"最近几步刚分配的块"，而是在保护
**全体**。那个 0.5 s/轮 的怪值，本质是在用错误的参数掩盖结构错误。

## 逐出策略

| 策略 | 规则 | 用途 |
|---|---|---|
| LRU | 最久未访问 | 基线（= vLLM 默认） |
| LFU | 访问次数最少 | 基线（在本 workload 上意外地强） |
| GDSF | `(base − origin) + cost_per_hit × hits / size` | Adaptive 的排序内核，可单独跑作对照 |
| Adaptive | GDSF + 年龄规则 + 热块规则（带夹断） | 本项目的提案 |

Adaptive 的三层设计理由、以及"绝对阈值不可迁移"的量化证据（同一个 T=50 在
long-summarize 上保护 98.9% 的块、在 legacy-c1 上只保护 27.0%，**极差 72.6 个
百分点**），都写在 `include/eviction_policy.h` 的类注释里，常数由
`scripts/derive_thresholds.py` 从 `../kvcache-tracer/traces/*.jsonl` 现算。

### 踩过的坑：GDSF 的通胀会无界增长，把排序退化成 FIFO

留痕（这是本项目自己撞上的第二类"静默退化"）。GDSF 的通胀 `L` 每次逐出抬到
被逐出者的分数，且只涨不落；而频率项的尺度是 `cost_per_hit × hits ≈ 0.77 × hits`。
实测（60 请求 / 254 槽，模拟器）：

| 请求数 | L | GDSF miss | LFU miss | LRU miss |
|---|---|---|---|---|
| 20 | 64.3 | 34.7% | 33.5% | 73.2% |
| 40 | 99.5 | 54.6% | 40.1% | 80.8% |
| 80 | 214.3 | 74.0% | 45.8% | 90.7% |

L 涨到 214 之后，**一个刚插入、0 次命中的新块，分数高于一个有 200 次命中的老块**，
于是排序退化成"逐出最老的" —— 而 LRU 在 80 请求那档是 90.7%。GDSF 悄悄变成了 FIFO。

修法是加一条**不变量**而不是调参：

```
L − origin ≤ max(频率项 over 驻留块)
```

通胀的用途是给冷启动垫一脚，不是压倒真实热度；一旦压过了就整体平移到 0
（`origin = L`，O(1)，不改任何两块之间的相对次序），重基准次数计入报告。
修完模拟器上 80 请求那档 74.0% → 60.0%；真库上 50% 预算那档
**69.80% → 57.10%**（见上面"修复通胀退化前后的真库实测"）。

⚠️ 这张表是**模拟器**上发现问题时跑的，留作发现过程的记录。**结论以真库那组为准** ——
这正是上面"踩过的坑"那一节的教训：模拟器和真库要对账，不能各说各话。

另外一条独立结论：**本 workload 上 GDSF 仍然输给纯 LFU**。因为所有块的 size 相同，
`cost/size` 提供不了频率之外的任何信号，于是 GDSF 与 LFU 的唯一差别就是这个通胀 ——
而通胀对 KV cache 的前提不成立：Web 代理里新抓回来的对象常常再也无人访问，所以要
挡住它；KV cache 里刚分配的块**几乎必然**马上会被读。这是合成 workload 的结构性
局限（它让一个请求的所有块访问次数完全相关），也是下一步该用真实 trace 重放验证的点。

## 与 CXL 的关系

CXL 在硬件层做同样的事 —— 让 GPU 透明访问外部内存池。本项目的"冷池"是 CPU DDR
（通过 PCIe）。**管理逻辑是通用的**：无论 CXL 还是 PCIe，你都要决定"换哪个 block"、
"什么时候换"。差别只在代价：本项目实测单块换回约 52.4 µs、D2H 渐近带宽 17.5 GB/s，
而 CXL 理论上是 200 ns 级、带宽相近。

（骨架版 README 这里写的是"~25us"，那个数字**在本仓里无处可考** —— 它声称来自
"Step 0 的 PCIe benchmark"，而那个 benchmark 不存在。现在引用的是项目一实测的
`pcie_link_ceiling.txt` / `pcie_interference_redline.txt`。）

## 已知限制

- **合成 workload 的结构性偏差**：一个请求的所有块访问次数完全相关，这让纯频率
  策略（LFU）表现得比真实场景更好。下一步应该用项目一的 trace 做重放
  （`kvcache-tracer/scripts/replay.py` 已经在那边了）。
- **冷池没有自己的逐出策略**：冷池满时 `evict_to_cold` 直接返回 `ERR_CPU_OOM`，
  块留在 GPU。真机上这一层是项目一 Step 4.8 研究的东西，值得单独做。
- **不是线程安全的**：CUDA 上下文是 per-thread 的，一个句柄只能在创建它的线程里用。
  真系统里管理线程和推理线程是分开的，需要一层排队。
- **没有和 vLLM 集成**：`GUIDE.md:496` 明写"你不必真的和 vLLM 集成"。本项目的
  接口是按 vLLM 的 `kv_offload` 分层的形状设计的（策略只用可换出集合、pin 归管理器），
  但没有实际接。
- **策略开销在大驻留集上是真问题**（Q4）：8192 块时 Adaptive 每次决策 81 µs，
  超过一次换出的代价。上真机前需要按驻留集大小分档，或者改成增量数据结构。
- **干扰测量的分辨率只有 ~1%**：`test_copy_slows_compute` 三次运行给
  +0.48% / +1.13% / +2.46%，符号稳定但幅度散。也就是说**小于 1% 的效应测不出来** ——
  能做的是"确认它在、方向对"，还做不到"把它定准"。要定准得上 CUPTI/Nsight，
  或者在真实 decode 循环里做长时程统计（项目一那条路）。
- **干扰测试用的不是 attention kernel**：`memwork_kernel` 是个流式读带宽的
  内核，和 attention 的访存模式（KV cache 随机访问 + 共享内存 staging）不一样。
  所以那 ~1% **不能直接当作"推理会被拖慢 1%"**，只能当作"这个方向上的效应存在"。

## 学习目标

做完这个项目，你会理解：

- **GPU 显存管理的底层机制**：pinned memory 为什么必需、arena 为什么比
  `cudaMalloc`/`cudaFree` 好、哪些 CUDA 调用是隐式同步点（`cudaMallocHost`、
  非 `cudaMallocAsync` 指针的 free）
- **异步数据迁移**：CUDA stream 的语义、事件如何建立跨流依赖、
  "重叠"怎么才能被**证明**（负对照）、以及为什么重叠不等于免费
- **缓存替换策略的设计和评估**：为什么绝对阈值不可迁移、退化怎么才能**可见**、
  确定性为什么是可复现性的前提
- **为什么 CXL 被认为是"数据中心的下一件大事"**，以及在那个世界里策略的位置
